# Compositor placement research

## v1 decision and evidence boundary

The v1 compositor target is **Hyprland only**. Niri is post-v1 and unverified. The placement and output-selection measurements below were made on Hyprland `0.56.2`, GTK `4.22.5`, gtk4-layer-shell `1.3.0`, Go `go1.27.1-X:nodwarf5 linux/amd64`, Linux `7.3.0-rc3-1-cachyos-rc`, with the isolated gotk4 `v0.4.1` probe. This is the tested version tuple, not a claim that all Hyprland `0.56.2` use cases are complete or that lower/later versions work. The probe is a nested research module; the production overlay remains owned by Issue #32.

For v1, use overlay layer, production namespace `azerlay`, keyboard mode none, exclusive zone `-1`, nine configured anchors, and signed X/Y margins. On a centered axis, positive margins move right/down and negative margins move left/up. The existing `overlay.monitor` remains an opaque string: empty delegates output choice to the compositor; a nonempty value selects an exact connector first or, if no connector matches, a unique exact GDK description. Missing or ambiguous explicit selection keeps the overlay hidden. When its selected output disappears, keep input/configuration state and hide the overlay without migration; show it only after the same configured key uniquely resolves again. A matching key is not a permanent physical monitor identity.

The first live headless-output removal test demonstrated hiding, but direct same-name recreation in the unmodified host session aborted the probe on a GDK scale assertion and crashed Hyprland. Later isolated sessions restored the same probe on a Wayland-backed virtual output and, with a temporary GBM allocation workaround, on a headless output. A subsequent live-host test caught a brief migration to DP-1 during removal. After the probe was changed to hide on GDK monitor invalidation, both a controlled disabled-then-enabled return and a direct same-name headless recreation on the host restored the same probe without an observed migration or crash. These later successes do not establish the cause of the earlier crash. The local `.omo/evidence` paths below identify earlier run artifacts; the new live-host command output and observations are stated in the decision without a new artifact file.

## Monitor identity (Issue #41, Todo 3; 2026-09-23)

The existing opaque `overlay.monitor` value uses this v1 selection policy: an empty value delegates output choice to the compositor (`default` in the probe); a nonempty value first matches an exact GDK connector, then a unique exact GDK description. A missing or ambiguous explicit match stays hidden. An explicit output's removal must hide the overlay while retaining state, with no migration to another output. Reappearance means the same configured key uniquely resolves again. Connector names can be renumbered or reused and descriptions are not proven permanent hardware identifiers, so a same-key return is not proof that the same physical device returned. The tested GDK accessor set exposes connector, description, manufacturer, and model but no proven persistent physical ID. No new config field is selected.

The live GDK preflight used `/usr/bin/python3` with GTK 4 initialization and `Gdk.Display.get_default().get_monitors()`. It found two monitors, one exact `DP-2` connector and one exact match for that monitor's description; only counts and availability were written to `.omo/evidence/probe-todo3/gdk-selector-preflight.log`. A `hyprctl monitors -j` projection recorded only connector names and description availability in `.omo/evidence/probe-todo3/hyprland-monitors.json`. The raw description, which may include a serial, stayed in memory. For the description run, the shell set `AZERLAY_TARGET_DESCRIPTION` from the GDK DP-2 monitor and passed `"$AZERLAY_TARGET_DESCRIPTION"` as one quoted probe argument; the transcript records that variable reference, not its value.

Each observed selector run used `env XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-1 GDK_BACKEND=wayland GSK_RENDERER=cairo G_DEBUG=fatal-warnings /tmp/azerlay-placement-probe --placement bottom-right 24 24 MONITOR -1` in an interactive `script -q -f -e -c` session. `MONITOR` was `default`, `DP-2`, the in-memory GDK description, or `DOES-NOT-EXIST` as indicated below. While the probe was mapped or waiting, `hyprctl layers -j` was filtered to namespace `azerlay-placement-probe` across all outputs. The local Wayland socket, Hyprland session identifier, and temporary binary path describe this observation, not required product settings.

The planned v1 production behavior remains hidden with state retained until the configured key uniquely resolves again. This first attempt did not verify the return path.

Post-crash inspection of the host core (Hyprland PID 2095) found `SIGFPE/FPE_INTDIV` at `CHeadlessOutput::scheduleFrame` with the `idiv %rcx` divisor register equal to `0`. The installed Aquamarine `0.15.1` source divides the frame interval by the active mode's refresh rate without checking for zero ([Headless.cpp](https://github.com/hyprwm/aquamarine/blob/f31c47a1b9d300847d8fc3108ad959448103dfc1/src/backend/Headless.cpp#L80-L89)); Hyprland `0.56.2` calls it while applying the monitor rule ([Monitor.cpp](https://github.com/hyprwm/Hyprland/blob/efb50993780079460b0cbed1363e2166a2de1d9f/src/output/Monitor.cpp#L1048-L1056)). Hyprland has a non-DRM fallback that can set a custom mode with refresh rate zero when candidate modes fail ([Monitor.cpp](https://github.com/hyprwm/Hyprland/blob/efb50993780079460b0cbed1363e2166a2de1d9f/src/output/Monitor.cpp#L919-L937)), but the core and retained logs do not establish why the normal 60 Hz headless mode was not used on this return. The probe's earlier `SIGABRT` was caused by the test invocation's `G_DEBUG=fatal-warnings` turning GDK's `gdk_monitor_set_scale` warning into an abort; that warning still indicates an invalid transient monitor scale, and removing the flag would not prevent the compositor's zero division. Neither crash identifies a proven defect in the probe's monitor-selection code.

The installed Aquamarine `0.15.1` and the inspected upstream source still have this unguarded division. Until the zero-refresh path is resolved and validated in isolation, repeating the direct headless remove/recreate sequence on the host session risks another compositor crash. The nested Wayland-backed output test below gave an early same-key reattachment observation but did not fulfill the headless return criterion by itself.

A post-crash control run on the restarted live host used a freshly built probe with `G_DEBUG` unset and explicit `DP-2`: it mapped on `DP-2`, reported an empty input region, answered `status`, and exited 0 on `quit`. A subsequent `hyprctl monitors -j` still showed DP-1 and DP-2 at their original modes, `hyprctl layers -j` showed no remaining probe layer, and no new Hyprland/probe core appeared. This checks the stable-output probe path; it does not exercise output removal or return.

After the crash, the restarted Hyprland `0.56.2` session reported only DP-1 and DP-2, both scale `1`, `reserved=[0,44,0,0]`, with zero `azerlay-placement-probe` layers. `pgrep -af '^/tmp/azerlay-placement-probe'` found no running probe (`.omo/evidence/probe-todo4/aftermath.md`). This is a cleanup observation, not evidence that same-key return succeeded. No physical hotplug, lower or later Hyprland version, or persistent physical-output identity was tested.

### Isolated same-name headless return with a GBM workaround (2026-09-23)

A third Hyprland `0.56.2` instance ran nested on the host Wayland socket, with its own `wayland-2` socket and `WAYLAND-1` output. Its minimal Lua config selected `azerlay-probe` at `1920x1080@60`, scale `1.25`, and 10-bit depth. Without a workaround, `hyprctl output create headless azerlay-probe` returned `ok` but the output stayed `0×0`; Aquamarine logged GBM `bo null` allocation failures. A direct GBM check on `/dev/dri/renderD128` found that a `1920×1080` XR24 buffer could be allocated with flags `4` (rendering) or `5` (rendering and scanout), but not `20` or `21` (the same flags with linear). The nested attempt logged calls with flags `21`. For this isolated process only, a temporary `LD_PRELOAD` wrapper cleared `GBM_BO_USE_LINEAR` from `gbm_bo_create` calls at `1920×1080`. No system library or host compositor was changed. With that wrapper, `hyprctl monitors -j` confirmed `azerlay-probe` at `1920×1080@60`, scale `1.25`, rather than relying on the creation command's `ok` response.

The freshly built probe ran on the nested socket as `--placement bottom-right 24 24 azerlay-probe -1`, with `G_DEBUG` unset. Its initial status was `resolution=connector mapped=true actual=connector="azerlay-probe"`, with an empty input region. `hyprctl layers -j` placed its `160×80` layer at `(2302,760)` on `azerlay-probe`, whose logical origin was `(950,0)` and size `1536×864`. While this same probe process remained running, `hyprctl output remove azerlay-probe` left only `WAYLAND-1`; the probe answered `status` with `resolution=missing selector mapped=false actual=none`, and no probe layer remained on the available output. `hyprctl output create headless azerlay-probe` then restored an active `1920×1080@60`, scale `1.25` output. The original probe process answered `status` with `resolution=connector mapped=true actual=connector="azerlay-probe"`; its empty input region was reapplied, and `hyprctl layers -j` again placed the layer only on `azerlay-probe` at `(2302,760)`. The probe exited 0 on `quit`. After stopping the isolated compositor, the host still had only DP-1 and DP-2 at their original modes.

This verifies same-name reattachment on a real headless backend under the stated GBM workaround. This isolated run alone did not verify the unmodified host-session return or eliminate Aquamarine's zero-refresh division. The probe emitted a mapped notification during output removal before its next 50 ms monitor-list poll destroyed the surface; no concurrent layer capture established whether that brief transition could appear on the other nested output. The observed stable absent and restored states had no migration, but transient migration remained unverified in this run.

### Live-host removal transition and controlled return (2026-09-23)

On the live Hyprland `0.56.2` host, DP-1 and DP-2 retained their original settings. The explicit `azerlay-probe` headless output was configured at `1920x1080@60`, scale `1.25`, and the running probe used `--placement bottom-right 24 24 azerlay-probe -1`. Before the invalidation fix, `hyprctl output remove azerlay-probe` made the selected output disappear. Sampling `hyprctl layers -j` at approximately 5 ms intervals caught the probe layer on DP-1 at monotonic times `279442.795` and `279442.807`; it was absent by `279442.845`. Thus the earlier stable absent-state snapshot did not establish no transient migration. Recreating the headless output with a monitor rule first setting `disabled = true`, then enabling it with `disabled = false`, mode `1920x1080@60`, and scale `1.25` restored the same running probe only to `azerlay-probe` at `(5832,760)`; it reapplied the empty input region. This was a controlled return, not the direct recreation sequence that had crashed earlier.

The probe was then changed to hide its surface in the GDK monitor-invalidation handler before gtk4-layer-shell's later handler could retarget it. A fresh binary first mapped the `DP-2` control at `(4296,1336,160,80)`. In one live-host headless cycle, the probe initially mapped only on `azerlay-probe` at `(5832,760)`. After `hyprctl output remove azerlay-probe`, the probe reported `notify::mapped=false` and `resolution=missing selector mapped=false`; a `hyprctl layers -j` poll recorded 1,495 samples over 12 seconds, showing only the initial `azerlay-probe` layer followed by no probe layer. No DP-1 or DP-2 migration appeared in those samples. The same probe process then survived the controlled `disabled = true` recreation and `disabled = false` enable at `1920x1080@60`, scale `1.25`; it mapped only on `azerlay-probe` at `(5832,760)` and reapplied the empty input region. No probe or compositor crash occurred in this cycle. Cleanup removed the temporary output and probe and reloaded only the original monitor configuration; DP-1 and DP-2 had their original settings and no probe layer remained.

The mapped notification and sampled layer states support this one transition's observed ordering and absence of migration in the captured poll. They do not prove that every intermediate compositor frame was sampled. The ordinary direct same-name headless create/remove/create path on the previously unmodified host had produced GDK `SIGABRT` and Hyprland `SIGFPE`; this controlled disabled-then-enabled result alone did not establish that ordinary path was safe. The probe test did not verify retention of production input or configuration state, and no physical hotplug was performed.

A further live-host test used the fixed probe with `G_DEBUG` unset. With `azerlay-probe` absent, the host first set `hl.monitor({ output="azerlay-probe", disabled=false, mode="1920x1080@60", position="auto", scale=1.25 })`, then ran `hyprctl output create headless azerlay-probe`. The output reported `1920x1080@60`, scale `1.25`; the probe reported `mapped=true`, and `hyprctl layers -j` placed its `160×80` layer only on `azerlay-probe` at `(5832,760)`. With the same probe running, `hyprctl output remove azerlay-probe` produced `notify::mapped=false` and `resolution=missing selector mapped=false`. A roughly 5 ms `hyprctl layers -j` poll over 10 seconds captured 1,245 samples: the selected-output layer followed by no probe layer, with no DP-1 or DP-2 migration observed. Direct `hyprctl output create headless azerlay-probe`, without a disabled-output step, returned an active `1920x1080@60`, scale `1.25` output. The original probe reported the selected output and `mapped=true`, reapplied its empty input region, and appeared only on `azerlay-probe` at `(5832,760,160,80)`. Neither the probe nor Hyprland crashed in this cycle. This is a positive live-host observation for direct same-key return, but does not identify or establish a fix for the earlier GDK `SIGABRT` or Hyprland `SIGFPE`; it does not test production input/configuration state or physical hotplug.

### Handoff to Issue #32

The production bridge should implement the selected v1 contract on GTK's locked main OS thread: initialize gtk4-layer-shell with namespace `azerlay`, overlay layer, keyboard mode none, nine-anchor/margin mapping, exclusive zone `-1`, and an empty GDK input region on every mapped surface. The probe's `azerlay-placement-probe` namespace and fixed `160×80` surface are research fixtures, not production settings. Avoid changing the root Go module dependency boundary solely for this decision.

Resolve the configured output from the current GDK monitor list using connector-first/unique-description selection. For an unresolved explicit key, keep the overlay unmapped while the reducer's input/configuration state continues; do not migrate to the compositor's default output. When the selected `GdkMonitor` emits `invalidate`, hide the surface synchronously before gtk4-layer-shell's after-handler can temporarily retarget it to the default output. Then discard the invalid surface and immediately resolve the configured key against the current monitor list; re-resolve it on future monitor-list changes as well. Show a new surface only when that key uniquely resolves. Disconnect handlers for invalid surfaces and reapply the empty input region after each actual map. No new `overlay.monitor` field or persistent hardware identifier is defined.

The controlled and direct live-host returns each address one headless removal and same-key return cycle, including sampled removal transitions. The successful direct cycle is a positive observation for Issue #41's F3 headless return criterion on this tested host and version tuple. The earlier GDK/Hyprland crash did not recur, but its cause and the zero-refresh path were not established as fixed. Production input/configuration state retention, compositor-originated remap, and physical hotplug remain unverified. The prior [ABI decision](overlay-abi.md) remains the authority for GTK pointer ownership and click-through observations; these placement measurements do not replace it. Issue #41 is closed as research; Issue #32 owns production implementation and validation.
